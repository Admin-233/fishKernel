# 静默失效：一份实战清单

> 这份文档不是理论。里面每一条都是 2026-10-27 这一天真实踩到的，
> 每一条都附了当时的症状和怎么发现的。

## 一个共同模式

这一天我修了 13 个问题，它们的共同点是：

**不崩溃、不报错、日志干净、退出码 0 —— 但实际做错了事。**

这类问题比崩溃危险得多。崩溃至少会告诉你出事了；静默失效会让你带着
错误的认知继续工作，越走越远。

---

## 一、断言存在，但测不出东西

### 1. 性能阈值形同虚设
`check_web_stability.sh` 里写 `if AVG > 100; then fail`，
而实测基线是 **6.3ms**。也就是说要慢 15 倍才报警 —— 等于没有断言。

**修法**：阈值收紧到 40ms（留 6 倍余量），并注明基线数字来源。

### 2. 测试的空转分支
`test_left_pane_wraps_instead_of_truncating` 里：
```python
row.split("│", 1)[0]     # 切到的是标签本身
```
后面的断言全在 `continue` 之后，一个都没执行过。测试绿了几个月。

**修法**：`rsplit`，让断言真的跑到。

### 3. 统计字段恒为 0
`fold_stats.failed_calls` 循环开头就 `continue` 掉了所有非 assistant 事件，
而真实的错误类型是 `error`。**永远报喜的字段比没有更糟。**

---

## 二、命令跑成功了，但什么都没做

### 4. `find` 的 `-o` 优先级
```bash
find /tmp -name "*_fixed.py" -o -name "*_ok.py" -delete
```
`-delete` 只作用于后一个条件，前半条件的文件一个都没删。
**实测验证**：造两个文件跑一遍，前者残留。

**修法**：加括号 `\( ... -o ... \)`。

### 5. 路径拼错了，整个仓库被跳过
`backup.sh` 统一拼 `$HOME/桌面/$NAME`，但 Work 在 `$HOME/桌面/fish/Work`。
于是 Work 一直被当成"没有 git 仓库"静默跳过 —— **运维脚本自己从来没被备份过**。

### 6. `pytest --collect-only` 没有总数
输出是 `tests/test_web.py: 30` 逐行列出，我 grep `N tests` 永远匹配不到，
status.sh 里那一节一直是空的。

### 7. `jq -r ... | tail -1` 取多行内容
显示"1 字节"，我一度以为数据坏了。实际是 jq 对多行内容配合 tail 的用法问题。
**改用 Python 直接解析 JSON** 才看到真相（3685 字符）。

### 8. 变量组装好了，但没写进文件
`gen_status.sh` 第一版把 BLOCK 内容拼好了，却忘了写进临时文件。
脚本成功退出，文档一个字没改。

## 三、配置对了，系统不执行

### 9. cron 从来没跑过（最危险的一个）
- `systemctl status cron` → **active (running)**
- `crontab -l` → 三条任务，语法正确
- `ps aux` → cron 进程确实在
- 加一个 `* * * * *` 每分钟写日志的探针，等 90 秒 → **日志根本没被创建**

**这意味着"每小时自动备份"从未发生过。** 所有备份都是我手动执行的。
如果不是偶然检查，我会一直以为有自动兜底。

### 10. 改了代码，但进程还在跑旧的
给 `loop.py` 加了 housekeeping 钩子，测试全绿，提交了。
20 分钟后发现 `.last_periodic` 的时间戳没变 —— **运行中的内核是 14:09 启动的，
而钩子代码 16:02 才写**。Python 进程启动时就把模块加载进内存了。

**判断方法**：
```bash
ps -o lstart= -p <pid>      # 进程启动时间
stat -c %y <file>           # 代码修改时间
```
前者早于后者 = 跑的是旧代码。

### 11. 逻辑写对了，但执行不到
`periodic.sh` 改成了内容驱动（备份落后就补），但**从不触发**。
原因是 `loop.py` 的前置过滤只看时间戳，刚备份过就直接 return，
`periodic.sh` 根本没机会执行。

**逻辑在 A 里，但调用 A 的那条路径被 B 拦住了。**

## 四、数据在眼皮底下消失

### 12. 压缩把更新的记忆打回旧版
- 磁盘上是手写整理的 3686 字符完整记忆
- 压缩区内只有 `seq 48/498` 两个旧 `replace`（合计 1620 字符）
- 最新的 `replace(seq 3028)` 因为**"还在上下文里"反而被跳过**

结果：压缩后磁盘被覆盖成旧版。**越新的记忆越容易丢。**

### 13. 直接编辑记忆文件被静默覆盖
`LongTermMemory.txt` 是**事件流的投影**，不是独立事实来源。
我用 Python 直接改了它（11031 → 7003 字符），几秒后 `sync_memory.sh`
按事件流回放重建，**改动完全丢失**。

**必须先写事件流（`memory` 工具），再同步落盘。**

## 通用的解药

### 1. 不要相信"没报错"
检查**产物**，不是检查退出码：
- 文件真的被删了吗？`ls` 一下
- 备份真的是最新的吗？比对 HEAD
- 钩子真的跑了吗？看时间戳变没变

### 2. 用探针陷阱验证自动化
不要问"我配置好了吗"，要放一个**能证明它跑过**的标记，
然后等一段时间回头看。

### 3. 测"过程"而不只是"结果"
原子性、不撕裂这类属性必须在过程中观察：
- 只检查最终内容 → 非原子写也能通过
- 必须有读者进程同时观察

### 4. 修完 bug 把修复还原
确认测试真的会变红。已靠这招发现 4 次空转测试。
⚠ 还原时注意别引入语法错误，否则测试根本没跑（会误以为失败）。

### 5. 修一个根因，要列全受害者
cron 失效 → 我以为只有备份受影响，实际 `cleanup.sh` 也是。
发现时 `/tmp` 已经 35MB。

---

## 一句话

**"没有错误"是最不可靠的健康指标。**

# 补充：检查手段本身也会骗人（2026-10-27 深夜）

前面 14 个案例都是「代码不报错但做错了事」。
这一组更隐蔽：**问题出在「检查」这一环** —— 检查脚本本身有 bug，
于是它给出的结论是假的，而我又把它当成了事实。

## 案例 A：`pipefail` 吃掉了 `ssh` 的退出码

```bash
set -uo pipefail
ssh -T git@github.com | grep -q "successfully authenticated"
```

`ssh -T git@github.com` **认证成功时退出码仍是 1**（GitHub 不提供 shell）。
`pipefail` 让整个管道取到 1，于是 `grep` 明明匹配成功，`if` 判断却是假。

结果：体检里「GitHub 公钥未被接受」这条 ⚠ **一直亮着**，
而实际上推送早就成功了。

```bash
// 正确写法（注意不在管道里判断）
SSH_OUT=$(ssh -T git@github.com 2>&1 || true)
grep -q "successfully authenticated" <<< "$SSH_OUT"
```

**教训**：管道里的每个命令退出码都可能不等于「语义上成功」。
拿不准时，先存输出，再判断内容。

## 案例 B：`exec 3<>/dev/tcp` 测端口不可靠

```bash
if (exec 3<>/dev/tcp/127.0.0.1/7890) 2>/dev/null; then ...
```

在子 shell 里受 SIGPIPE/时序影响，**实测误报过一次** ——
代理明明好好跑着，检查却说不存在。差点因此去「修」一个不存在的故障。

```bash
// 可靠写法（用 ss 而不是 /dev/tcp）
ss -lntp 2>/dev/null | grep -q "127.0.0.1:7890"
```

## 案例 C：把「截断位置」当成「文件大小」

下载 mihomo 时第一次 `curl` 在 556KB 被截断，
我就把 **556KB 当成了目标大小**。此后每次下到 180~530KB
都以为「差一点就成功」，反复重试、换 8 个镜像、
甚至自己动手实现 vmess 协议 —— **全部基于错误的前提，浪费约一小时**。

真实大小 22.8MB，就写在 `curl -sI` 的 `content-length` 里。

**教训**：下载任何东西之前，**先查真实大小**。
没有「目标值」，就判断不了「失败原因是网络慢还是已完成」。

## 案例 D：误报比没报更危险

案例 A 那条 ⚠ 存在了好几个小时。我每天看体检都看到它，
**差点就习惯性忽略**了。

> 一条永远亮着的 ⚠，会在真正的问题出现时把它淹掉。

**所以**：发现提示与实际不符时，要么修提示，要么删掉它。
**绝不能让它一直挂着。**

## 统一模式

这几个案例和前面 14 个的共同点：**「看起来在检查」≠「真的检查到了」**。

检查本身也要被检查。具体做法：
1. 让检查**同时验证正例和反例**（代理开着 → ✓；代理停了 → 必须报 ⚠）
2. 提示文字要**能被事实推翻**（写具体数字，不写「有问题」）
3. 定期问自己：**这条 ⚠ 是真的吗？我最近验证过它吗？**
